# 旅行规划

交付能在路上使用的攻略。国庆是首批场景，不限制年份或假期。攻略推荐不包含代订、付款。默认生成独立 HTML；TREK 是可选在线增强，不阻塞本地交付。

## 核心会话流程

开始规划时先读 [三种入口与会话步骤](references/interaction-workflow.md)，按用户已提供的内容判断入口，不要求用户重复填写问卷：

- 已有基本行程：保护已订车票、酒店和必去安排，先查冲突，再补缺口。
- 不知道怎么玩：区分目的地未定与目的地已定，先选方向和节奏，再查具体候选。
- 提供链接/截图：先读材料、提取地点与偏好，确认哪些必须保留，再补充搜索。
- 混合输入同时保留已有约束与收藏；不是三选一。每轮只补问影响下一步的少量问题。

**高德地点/路线/地图与FlyAI票房查询，优先读取并使用 [托管查询服务](references/hosted-service.md)。** 脚本首次查询自动领取体验凭证、到期自动续领，无需用户找维护者逐个领凭证或配置上游Key；服务不可用或用户选择自有账户时，再走下面的独立渠道配置。多个地点先去重，再用service.py串行查询，保存成功结果后只补剩余项；不得并发curl或快速循环绕过脚本节流。地图生成后通过 `service.py prepare-maps` 接到当前C版，不能只留OSM底图。

首次需要某个渠道时读取 [环境准备与用户接力](references/channel-setup.md)：先检查当前工具、连接与授权，只引导缺失步骤；分别验证安装、浏览器连接、网站登录和API查询，成功后继续原任务。

随后读取 [平台职责与调用时机](references/channel-playbook.md)。平台按信息缺口调用，不要求先把所有账号登录一遍。登录可由用户扫码接力；验证码或风险限制出现后停止该平台采集，不通过随机延迟或重试绕过。随机间隔只是保守采样节奏，不能保证不触发风控。

用 [规划工作包与页面交接](references/planning-handoff.md) 保存当前版本的约束、来源、候选、决定和缺项。修改日期/酒店/人数后，按依赖关系重新查询，不覆盖用户已订与已付记录。用户确认针对具体版本，不能把“你来推荐”当成已订票。

旅后照片读取 [旅后纪念](references/memories.md)，在会话内处理。云同步按需读取 [TREK 接入](references/trek.md)；网页完成后的手机发布按下方手机交付环节执行，没有真实连接与验证不输出虚构网址。

## 先了解旅行

复用已知信息，集中补问真正缺失的内容：出发地、目的地是否确定、具体日期及年份、同行人数和节奏、预算范围与总额/人均口径、固定交通和住宿、必去点。可以接收收藏链接、截图或文字。老人、儿童相关只询问步行、休息、无障碍等实际需求。

目的地未定，先比较少量候选的交通可行性、季节、预算和体验，让用户选方向再深入。日期、人数、预算口径未知时不伪造精确预算；用户希望先看草案，可把假设列入待确认项。

## 调研与规划

**先完成研究，再交付页面。** 用户已有票和酒店只免去重新选票选酒店，不免去景点体验、餐厅和通勤查询。长沙示例中的“怎么玩、吃什么、怎么过去”需要有来源的体验资料、点评餐厅查询和地图通勤查询；小红书只在用户提供收藏或存在关键体验缺口时少量补查，公开资料充分时无需调用；收费景点门票优先查FlyAI。不要用模型常识、占位预算或演示材料替代真实查询后直接构建网页。

按 [研究留存与交付检查](references/delivery-evidence.md) 在私有工作目录逐次保存原始证据和 research-log.json，再建立渠道检查表（公开网页与配图、小红书、点评、FlyAI、高德），每项记录任务、状态、来源/查询时间、缺项与下一步。状态区分：待查询、已读结果、复用已有证据、待用户配置、受阻、无需调用。无需调用必须说明理由（例如车票酒店已订且无待查门票）；工具不存在要先走配置引导，不能悄悄跳过。用户明确不使用某渠道或资料已充分时可以采用替代来源，但要说明。

生成前在对话里简短反馈各渠道实际结果与未完成项。尚未采集而用户只想先看排版时可交草案，明确未研究，不宣称完整攻略。渠道检查记录留在私有工作目录，不把采集日志堆进网页。配置一项受阻时继续其他独立渠道，不以缺高德Key为由停止全部调研。


读取 [调研规则](references/research.md)。涉及小红书时读取 [帖子读取与工具选择](references/xiaohongshu.md)；MediaCrawler 默认停用。小红书、点评与人工扫码协作先读取 [浏览器调研与采样节奏](references/browser-research.md)。使用当前环境实际可用且已授权的搜索、浏览器或社区工具；没有小红书工具也能工作。拿不到原帖就说明读取失败，使用用户提供的截图/文字或其他公开来源，不把摘要当全文。

涉及住宿、交通、预算或天气穿衣，读取 [报价、天气与携带清单](references/prices-weather-packing.md)。大交通、住宿和景区门票优先尝试FlyAI真实查询；门票须核对价格适用日期、票种与套餐内容；模糊掩码价保留未知。会话维护统一规划工作包，费用逐项记录条件，清单与每日穿着不可遗漏。

按区域合并地点、消歧、去重，再围绕固定交通住宿安排。每天包括吃饭、休息、转场和缓冲；必去点冲突时解释取舍，不擅自删除。明确预约截止、营业时段及信息来源。天气区分预报、历史参考、未知，超出预报窗口不编造逐日天气。

用户已取消景点拍照灵感：不再默认生成拍照指导或固定“查看详情”弹窗。地点卡直接展示影响出行的开放、预约与来源，保留导航和真实商家详情链接。旅后照片制作保留在页面最后的三个风格选择中。

每两个相邻行程节点之间展示转场：查询真实路线后优先推荐地铁直达，其次比较公交、步行、打车；不能凭坐标直线距离推断线路、耗时或费用。未确定酒店、饭店和车站不得跳过拼路线。收到用户确认已订的酒店/车票后，按 [地图与转场](references/maps.md) 同步地点、地图、时间和预算。

页面是会话规划的确认结果：Agent 先沟通约束、采集资料并核实价格/日期/地点，再让用户确认重要取舍后回填；页面中的手动修改只是补充，不能把采集和判断工作推给用户。

涉及地点选择、通勤方案与预算回填时读取 [Agent与页面的数据交接](references/agent-page-contract.md)。

## 生成与交付：只使用当前C版

读取 [工作包与页面交接](references/planning-handoff.md)，从 `examples/planning-demo.json` 理解字段（合成数据，不作真实行程）。先完成公开网页配图与研究留存，再补齐工作包并校验，构建当前C版：

```bash
python3 <skill目录>/scripts/planning.py validate /绝对路径/plan.json
python3 <skill目录>/scripts/delivery_check.py /绝对路径/plan.json
python3 <skill目录>/scripts/render.py /绝对路径/plan.json --out /绝对路径/新的攻略目录
```

输出 `index.html`、`page-packet.json`、`sources.json`、素材与运行组件。仅使用 `assets/current/template.html`；不让用户挑旧设计，不调用旧trip.py或开发目录样例。渲染器拒绝覆盖已有目录。

地点确认后读取并执行 [公开网页配图](references/place-images.md)：优先普通网页/图片搜索，查城市代表性景观封面，以及每个已选景点、酒店和餐厅的对应实景图。封面选广为人知的城市旅游名片（如杭州西湖全景、长沙橘子洲头或五一广场），不以集贤亭一类局部小景代替城市封面。地点卡严格匹配地点，酒店餐厅匹配具体分店；核对使用条件并实际验证图片加载。不能因小红书不可用而跳过公开网页搜索；无需为了配图调用小红书。

Agent先确认行程，页面直接呈现已选位置、时间和费用。地图去重显示地点，跨城远端车站不扩大目的地日地图；连线是游览顺序，不冒充路网导航。图片仅导出permitted素材，本地素材复制进输出；选有城市辨识度的封面，未知许可不冒用。

页面修改以trip_id和revision隔离；勾选、地点与费用可本地保存。用户可导出trip-changes.json交回对话：先核对trip_id及base_revision，再合并稳定ID上的修改并重查受影响路线。不能盲目把旧网页修改覆盖新工作包，也不能将网页新填地址视为已核坐标。新版本输出前主动提醒保存旧页调整。新名称查地址由Agent按渠道能力完成，不能假称离线页面自带在线POI查询。

运行攻略目录内的 `python3 serve.py`，用HTTP网址打开；按 delivery-evidence.md 在浏览器检查切日、地图、导航弹层、折叠通勤、费用、图片与清单并保存验收记录；正文数据/组件本地可用，在线底图、天气刷新、远程图片需要网络。不要把本机预览当公网入口。程序校验不证明资料真实；交付时说明未核实项与预算覆盖。

旅后照片保留末尾三种风格入口；实际处理在会话中按 [旅后纪念](references/memories.md) 执行，不承诺安装包自带三个照片Skill。

## 最后一步：手机交付

三类规划入口最终都进入 [手机交付与平台适配](references/deploy.md)。用户要求手机访问或发布时，检查当前Agent身份与实际可用的托管工具：豆包工作优先核实自身云电脑发布能力；Codex/ChatGPT有Sites则读取其发布Skill；WorkBuddy检查CloudBase等实际连接；其他平台按当前官方能力推荐一种方式并逐步引导。身份无法判断时按工具能力选择，必要时才询问平台，不凭模型名称猜测。用户仅需本地文件则不发布；没有提出发布时简短提供选项。

保留当前C版完整产物，交付实际HTTPS链接及可选二维码；核实权限、期限和国内手机可达性，临时预览不称长期托管。明确新生成地图有效至返程后第90天结束、本地调整不跨设备同步；发布凭证不进入网页。部署成功、手机实测与长期可用的证据分别记录。

## 阶段反馈与验收

维护流程时使用 [多场景验收集](references/interaction-scenarios.md)，记录实际对话与工具结果，不能把文档推演算作端到端实测。

对用户清楚交代进度，不能只说“已做好”。调研后说明实际读到了哪些材料、哪些受阻；生成后给可打开的文件；验收后分开说明实现、测试、未验证。价格要说怎么查、按什么单位计算，未知项是否覆盖总额。地图至少区分页面内显示、网页到正确POI、手机App唤起；照片至少区分提示词、实际输入编辑、成品检查。外部平台受限不宣称全链路通过。
